02 · Componentes y estilos

Al revisar la plantilla, la compilación fallaba por variables sin uso: count, setCount y una importación de StrictMode. Se eliminaron los estados sobrantes y después se activó StrictMode envolviendo App. StrictMode ayuda a detectar problemas durante el desarrollo.

ARCHIVO · src/main.tsx
import { StrictMode } from 'react'
import { createRoot } from 'react-dom/client'
import App from './App.tsx'
import './index.css'

createRoot(document.getElementById('root')!).render(
  <StrictMode>
    <App />
  </StrictMode>,
)

La página quedó organizada en Menu, Inicio, Servicios, Portafolio, Nosotros, Contacto y Piepagina. App conserva un único elemento main para el contenido principal; menú y pie quedan fuera.

El espacio exterior inicial venía del margen que el navegador aplica al body. El CSS que lo eliminaba no estaba importado. Se conectó index.css y se dejó esta base:

ARCHIVO · src/index.css, fragmento
*, *::before, *::after { box-sizing: border-box; }
body { margin: 0; }
margin es espacio exterior; padding es espacio interior. Quitamos el margen del body, pero conservamos padding dentro del menú para que logo y enlaces no queden pegados al borde.

03 · Menú, navegación y marca

El menú usa useState para saber si está abierto en celular y useRef para devolver el foco al botón al presionar Escape desde los enlaces. El estado cambia la interfaz; la referencia permite acceder a un elemento DOM concreto.

CÓDIGO DE CONSULTA · fragmentos, no es un archivo completo
const [isOpen, setIsOpen] = useState(false)
const toggleRef = useRef<HTMLButtonElement>(null)

// Dentro del botón:
onClick={() => setIsOpen((open) => !open)}

// Al cerrar con Escape desde los enlaces:
setIsOpen(false)
toggleRef.current?.focus()

Se añadieron aria-expanded, aria-controls, nombres accesibles y estilos de foco. El menú adapta su distribución al ancho de pantalla y cierra al elegir un enlace.

Un enlace a /servicios solicita otra dirección al navegador. Como esta landing usa secciones, cambiamos las rutas por fragmentos:

ARCHIVO TSX · ejemplo de enlace y destino
<a href="#servicios">Servicios</a>
<section id="servicios">...</section>

El identificador debe coincidir exactamente. El desplazamiento suave está en App.css y se desactiva si el dispositivo pide reducir movimiento.

Logo: se probaron texto, una imagen generada, animación por recortes y un SVG geométrico. Los intentos de la letra A no gustaron y se volvió a la imagen PNG estática. No se afirma que la imagen generada sea idéntica al original. Logo.tsx conserva un experimento que el menú ya no importa.

Pie de página: Piepagina.tsx y Piepagina.css incluyen logo, llamada a contacto, navegación, servicios, año y enlace para volver al inicio. No se inventaron teléfonos ni correos.

04 · Git: local y remoto

Git registra versiones. GitHub aloja una copia remota. Tener una carpeta en tu equipo o crear un repositorio en GitHub no conecta ambos automáticamente.

ConceptoQué significa
Repositorio localArchivos e historial gestionados por la carpeta .git.
RamaUna línea de trabajo dentro del mismo repositorio.
Working treeTus archivos tal como están en el disco.
Staging / índiceContenido preparado para el próximo commit.
CommitUna versión guardada localmente.
originNombre asignado al repositorio remoto.
Push / fetch / pullEnviar commits / descargar historial / descargar e integrar.
Pull RequestPropuesta de integrar una rama en otra; todavía no es el merge.
TERMINAL · ejecuta estos comandos
git status
git branch --show-current
git remote -v
git --no-pager log --oneline -5

Crear una rama desde src también afecta a todo el repositorio. Git busca la carpeta .git en los directorios superiores.

TERMINAL · ejecuta estos comandos
git switch -c devops/ci-cd

switch cambia de rama y -c crea una nueva desde tu posición actual. Usamos devops/ci-cd para CI y luego devops/deploy para el despliegue.

El nombre de una rama organiza tu trabajo; no decide por sí solo cuándo corre CI. Eso se configura con los eventos del workflow.

07 · CI: archivo de referencia

Ubicación real: .github/workflows/ci.yml. Este contenido corresponde al archivo revisado al generar el manual. YAML usa espacios para la sangría.

ARCHIVO YAML · .github/workflows/ci.yml
name: CI PLOTIART

on:
  pull_request:
    branches: [main]
  workflow_call:
    inputs:
      publish:
        description: Preparar el artefacto para GitHub Pages
        type: boolean
        default: false

permissions:
  contents: read

jobs:
  validate:
    name: Revisar y compilar
    runs-on: ubuntu-latest

    steps:
      - name: Descargar código
        uses: actions/checkout@v6

      - name: Preparar Node
        uses: actions/setup-node@v6
        with:
          node-version: 24
          cache: npm

      - name: Instalar dependencias
        run: npm ci

      - name: Revisar código
        run: npm run lint -- --deny-warnings

      - name: Compilar proyecto
        run: npm run build

      - name: Guardar sitio compilado
        if: inputs.publish == true
        uses: actions/upload-pages-artifact@v4
        with:
          path: dist

08 · CI y tu primer Pull Request

Bloque de CICómo funciona
pull_request → branches: [main]Valida propuestas cuyo destino es main, al abrirlas o actualizarlas.
workflow_callPermite que otro workflow reutilice este trabajo.
inputs.publishBooleano; false por defecto. CD lo activa para guardar el resultado.
contents: readPermiso de lectura del código para el token del workflow.
validate / ubuntu-latestIdentificador del trabajo y entorno de ejecución Linux.
checkout / setup-nodeObtiene el código y prepara Node 24 con caché de npm.
upload-pages-artifactEmpaqueta dist para que el trabajo de publicación lo utilice. Solo se ejecuta si publish es true.

Al abrir un Pull Request no publicamos nada. El trabajo instala, revisa y compila. En la ejecución de CD, ese mismo workflow también guarda el artefacto.

TERMINAL · ejecuta estos comandos
git add .github/workflows/ci.yml
git --no-pager diff --cached
git commit -m "Configura CI para los pull requests"
git push -u origin devops/ci-cd

En el navegador: repositorio → Pull requests → New pull request. Elige base: main y compare: devops/ci-cd. Revisa los cambios, pon un título y crea la propuesta.

En Checks o Actions abre “Revisar y compilar”. Amarillo significa pendiente o en ejecución; verde, éxito; rojo, fallo. En tu primer PR la comprobación terminó correctamente. Después integraste con Merge pull request → Confirm merge.

CI verde no impide por sí solo integrar código que falla en otra ocasión. Para exigir estas comprobaciones hay que configurar reglas de protección o un ruleset. Esa protección no se configuró durante este recorrido.

09 · Preparar la publicación

GitHub Pages publica archivos estáticos. Vite prepara esos archivos en dist; no publicamos el servidor de desarrollo ni node_modules.

Para el repositorio plotiart se configuró esta ruta base:

ARCHIVO · vite.config.ts
import react, { reactCompilerPreset } from '@vitejs/plugin-react'
import babel from '@rolldown/plugin-babel'
import { defineConfig } from 'vite'

// https://vite.dev/config/

  base: '/plotiart/',
  plugins: [
    react(),

El sitio se publica bajo /plotiart/. base permite construir las direcciones correctas de los recursos. Si en el futuro publicas en la raíz de un dominio propio, normalmente usarías / como base.

10 · CD: archivo de referencia

Ubicación real: .github/workflows/deploy.yaml. El despliegue sigue siendo manual: un push o un merge por sí solos no publican la página.

ARCHIVO YAML · .github/workflows/deploy.yaml
name: CD PLOTIART

on:
    workflow_dispatch:

permissions:
    contents: read

concurrency:
    group: github-pages
    cancel-in-progress: false

jobs:
    build:
        name: Validar y preparar sitio
        if: github.ref == 'refs/heads/main'
        uses: ./.github/workflows/ci.yml
        with:
            publish: true

    deploy:
        name: Publicar en GitHub Pages
        needs: build
        runs-on: ubuntu-latest
        
        permissions:
            pages: write
            id-token: write
            
        environment:
            name: github-pages
            url: ${{ steps.deployment.outputs.page_url }}

        steps:
            - name: Configurar GitHub Pages
              uses: actions/configure-pages@v5
            
            - name: Publicar sitio
              id: deployment
              uses: actions/deploy-pages@v4

11 · Entender y ejecutar CD

Bloque de CDResponsabilidad
workflow_dispatchHabilita el botón Run workflow.
concurrencyLimita publicaciones simultáneas del mismo grupo; no garantiza desplegar toda ejecución intermedia.
if: github.ref == refs/heads/mainPermite construir para publicación únicamente desde main.
uses: ./.github/workflows/ci.ymlLlama al CI local del mismo commit. No se duplican los comandos.
publish: trueActiva la subida del artefacto de Pages.
needs: buildEspera a que la preparación termine correctamente.
pages: write / id-token: writePermisos que requiere el trabajo de publicación.
environment: github-pagesRegistra el destino del despliegue y su enlace. No equivale por sí solo a exigir aprobación humana.
deploy-pagesPublica el artefacto producido por el trabajo anterior.

15 · VPS y algoritmos privados

Una VPS es un servidor que administras. No se configuró ninguna durante este recorrido; esta página resume la arquitectura que hablamos como siguiente etapa.

CapaQué haría
CI en GitHub ActionsValida y compila; genera dist.
CD para VPSEnvía el artefacto mediante SSH y activa una nueva versión.
NginxEntrega los archivos estáticos al navegador.
Dominio y HTTPSApuntan al servidor y protegen el tráfico.
OperaciónActualizaciones, accesos, monitoreo, respaldo y recuperación a tu cargo.

Para esta landing estática no hace falta mantener Node ejecutándose en producción. Tampoco se usa npm run dev o npm run preview como servidor público. Si publicas en la raíz de un dominio, adapta la base de Vite.

Qué significa proteger tus algoritmos: el navegador recibe el HTML, CSS y JavaScript del frontend, incluso con un repositorio privado o una VPS. Minificar u ofuscar no lo convierte en secreto.

ARQUITECTURA · ejemplo conceptual
Navegador (React)
      │ envía datos por HTTPS
      ▼
API en el servidor
      │ ejecuta la lógica privada
      ▼
Respuesta con el resultado, sin entregar el código fuente

Una lógica sensible debe ejecutarse en el backend, con autenticación y límites adecuados. No envíes claves privadas al frontend. Un repositorio privado protege el acceso al repositorio; no evita que los visitantes inspeccionen el código que reciben.

Una VPS tampoco impide por sí sola el acceso del proveedor de infraestructura al servidor. Si ese fuera tu requisito, habría que estudiar otro modelo de confianza. No se implementó ningún backend ni migración a VPS.

Guarda dos cosas: este manual y una copia del código con su historial. El PDF documenta el aprendizaje; el repositorio contiene los archivos que puedes reconstruir.

TERMINAL · recuperar el proyecto en una carpeta nueva
git clone git@github.com:PedroClemente150198/plotiart.git
cd plotiart
npm ci
npm run dev

Ejecuta el clon desde una carpeta padre donde aún no exista plotiart. Para crear además un respaldo transportable de los commits y referencias locales:

TERMINAL · ejecuta estos comandos
git bundle create ../plotiart-respaldo.bundle --all

El bundle no incluye cambios sin commit, archivos sin seguimiento ni secretos ignorados. No guarda la configuración de Pages, los secrets ni el historial de ejecuciones de Actions. Guarda esas configuraciones por separado cuando sean necesarias.

Ejercicios para continuar:

  • Añade una tarjeta de servicio en una rama nueva y recorre el ciclo PR → CI → merge → CD.
  • En una rama de práctica, deja una variable sin uso, observa el fallo y corrígelo. No integres el error.
  • Añade una prueba útil del menú móvil; luego incorpora su ejecución a CI.
  • Configura una regla que exija CI antes de integrar en main. Comprueba las condiciones de tu cuenta.
  • Optimiza el PNG del logo conservando el original y compara el resultado visual.
  • Más adelante, practica staging, versiones de acciones fijadas por SHA y despliegues recuperables.
